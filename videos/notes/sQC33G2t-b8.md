# K사 개발자가 설명하는 클로드코드로 스펙주도 개발(SDD)하기

> 한 줄 요약: 클로드 코드는 초반엔 잘 되다가 규모가 커지면 규칙이 하나씩 깨진다 — 원인은 **우리가 정하지 않은 빈칸을 AI가 대신 채우기** 때문. **스펙주도개발(SDD)**은 "게시판 만들어 줘"(빈칸 99% 스펙)의 빈칸을 **미리 글로 채워 두는 것** — 핵심은 ①**어떻게가 아니라 무엇을**(구현이 아니라 목표) ②**사람이 아니라 AI를 독자로**. "코드가 진실 → **의도가 진실**"로 뒤집어, 버그도 코드가 아니라 **스펙을 고쳐 재생성**. 단 스펙만으론 부족(AI가 무시·매번 다른 코드)해 **검증 절차 필수**. 실습 도구 **GSD**는 결정을 디스크(.planning)에 파일로 남기고 작업마다 새 세션으로 컨텍스트를 깨끗이 유지.

## 1. 왜 규칙이 깨지나 — AI가 빈칸을 채운다 · [00:00](https://youtu.be/sQC33G2t-b8?t=0)
- **3줄 요약**
  - 클로드 코드는 초반 며칠은 잘 되다가 어느 시점부터 어제 고친 게 오늘 깨지고, 같은 규칙이 여기선 지켜지고 저기선 안 지켜짐 → 다시 설명하는 시간이 직접 짜는 시간보다 길어짐.
  - 원인은 **AI 특성**: 우리가 정하지 않은 것을 AI가 대신 정하기 때문. "게시판 만들어 줘"(7글자) → 회원가입·DB 구조·화면까지 수천~수만 줄의 결과.
  - 그 **간극을 AI가 혼자 채움**(로그인 방식·실명/익명·댓글 단계 등 우리가 말 안 한 것) — 이게 흔들림의 근원.
- **핵심 인용**: "저희가 정하지 않은 거를 AI가 대신 정해 주기 때문에 발생하는 일이에요."
- **내 질문**: '빈칸을 AI가 채운다'는 진단은 앞 영상(잭피디의 '질문해 줘' 한 줄, 신영선의 setup 인터뷰)의 '선명확화'와 정확히 같은 문제의식 아닐까?

## 2. ★스펙의 정의 — 무엇을·AI 독자로★ · [01:39](https://youtu.be/sQC33G2t-b8?t=99)
- **3줄 요약**
  - "게시판 만들어 줘"도 이미 스펙 — 다만 **빈칸이 99%인 부실한 스펙**. 스펙은 그 빈칸을 미리 글로 채우는 것.
  - 원칙 ①: **어떻게(구현)가 아니라 무엇을(목표)** 적는다. 원칙 ②: **사람이 아니라 AI를 대상**으로 쓴다 — AI가 마음대로 결정하게 두지 말고 사람이 먼저 구체화.
  - 이게 SDD(Spec-Driven Development, 스펙 주도 개발)의 전부. 핵심어는 **'주도'**.
- **핵심 인용**: "스펙은 어떻게 만들지가 아니라 무엇을 만들지를 적는 것 … 사람이 대상이 아니라 AI 대상으로 글을 쓰는 겁니다."
- **내 팁**: '무엇을·목표 중심'은 앞 영상(힉스필드 '기획 먼저')과 동일 — 비싼 실행 전에 싼 단계(스펙/기획)로 의도를 못 박는 절약 원칙.

## 3. 관계를 뒤집다 — 의도가 진실, TDD와의 닮음/차이 · [02:49](https://youtu.be/sQC33G2t-b8?t=169)
- **3줄 요약**
  - 기존: 코드부터 짜고 문서는 나중. SDD: **원본은 스펙, 코드는 스펙에서 뽑는 출력물**. GitHub Spec 발표 표현 — "코드가 진실이었다면 이제는 **의도가 진실**".
  - 그래서 버그도 코드를 바로 고치지 않고 **스펙을 고쳐 코드를 재생성** — 이게 '주도'의 뜻.
  - **TDD와 같은 뼈대**(약속 먼저, 구현 나중)지만 결정적 차이: 테스트는 초록/빨강으로 자동 판정, **스펙은 자동 판정이 안 됨**(→ 검증 절차 필요).
- **핵심 인용**: "코드가 진실이었다면 이제는 의도가 진실이라는 쪽으로 옮겨 간다."
- **내 질문**: '스펙을 고쳐 코드를 재생성'은 앞 영상(그래프 엔지니어링의 '상자 교체·되돌려 재실행')과 같은 '선언을 원본으로 다루기' 발상 아닐까?

## 4. 왜 지금 각광 + 두 한계(비용·비결정성) · [04:00](https://youtu.be/sQC33G2t-b8?t=240)
- **3줄 요약**
  - 작은 프로젝트는 바이브 코딩으로 충분(채울 게 적고 어긋나도 티 안 남). **규모가 커지면 불필요 API·충돌**이 누적 → 스펙을 먼저 써두는 방식이 각광.
  - 도구(GitHub Spec, AWS Kiro 등)는 많지만 **도구는 중요치 않음** — "스펙을 상세히 쓰고, 스펙 기반으로 코드 생성"이 핵심.
  - 스펙만으론 부족한 **두 한계**: ①**비용**(버그 하나에 장황한 마크다운 요구사항 재검토, 문서 리뷰가 코드 읽기보다 힘듦) ②**비결정성**(AI가 스펙 무시, 같은 스펙도 매번 다른 코드) → **검증 절차 필수**.
- **핵심 인용**: "스펙을 썼다고 해서 내가 이 프로그램을 온전히 통제하고 있다는 느낌 자체가 어쩌면 착각."
- **내 팁**: '검증 절차 필수'는 이 프로젝트의 품질 루프(build→**review/verify**→fix)와 동일 — 작성과 검증은 별도 레인.

## 5. 실습 — GSD로 결정을 디스크에 + 새 세션 컨텍스트 · [05:40](https://youtu.be/sQC33G2t-b8?t=340)
- **3줄 요약**
  - **GSD** 도구: `new project`로 요구사항을 대화로 계속 구체화 → 페이즈별로 나눠 하나씩 구현 → 마지막에 스펙대로 됐는지 **검증**. 복잡한 시스템은 안쪽에 숨기고 사람은 단순한 흐름만.
  - **컨텍스트 관리**: 작업마다 **새 세션(깨끗한 컨텍스트)**으로 시작해 이전 대화가 품질을 떨어뜨리는 문제 차단. 세션을 나가면 잃는 정보를 **디스크(.planning)에 파일로** 남겨 내일 새 세션에서도 결정 이어감.
  - `.planning` 구조: `project.md`(목표·비전) / `requirements.md`(범위: 만들 것·안 만들 것) / `roadmap.md`(전체 방향·단계) / **`state.md`(핵심: 진행·결정 갱신)** + 단계별 계획서·검증 기록. 흐름: **논의(구체화)→계획→페이즈 실행→검증→출시→(변경 시)다시 논의**.
- **핵심 인용**: "내가 했던 결정들을 다 파일에 남기고 디스크에 쓰기 때문에 … 이전에 결정했던 것들을 계속 이어 나갈 수 있습니다."
- **내 팁**: `.planning`의 state.md는 앞 영상(그래프 엔지니어링의 '작업일지 상태')·이 프로젝트의 `LESSONS.md`/`HANDOFF.md`와 정확히 같은 역할 — 중단·재개의 단일 진실원.

## TL;DR (5줄)

1. **문제**: AI 코딩은 규모가 커지면 규칙이 깨짐 — **우리가 정하지 않은 빈칸을 AI가 혼자 채우기** 때문.
2. **스펙(★)**: "게시판 만들어 줘"는 빈칸 99% 스펙. SDD = 빈칸을 미리 글로 채움 — ①**무엇을**(목표) ②**AI를 독자로**.
3. **뒤집기**: 코드가 아니라 **의도가 진실**. 버그도 스펙을 고쳐 재생성. TDD와 닮았으나 스펙은 자동 판정 불가.
4. **한계**: 도구(Spec/Kiro/GSD)는 부차적. 스펙만으론 **비용·비결정성** 때문에 부족 → **검증 절차 필수**.
5. **GSD(★)**: 결정을 `.planning`(project/requirements/roadmap/**state**.md)에 디스크로 남기고, 작업마다 **새 세션**으로 컨텍스트를 깨끗이 → 규모가 커져도 버팀. 결국 **빈칸은 사람이 채운다**.
