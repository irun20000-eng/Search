# 루프 엔지니어링 완벽 가이드 - 1 — 네 가지 루프 패턴과 검증 조건 설계

> 한 줄 요약: '루프 엔지니어링'은 사람이 프롬프트를 반복해서 치던 걸 **에이전트가 대신 프롬프트를 치게** 설계하는 것. 핵심은 **종료(검증) 조건을 잘 설계**하는 것 — 검수관(Evaluator) 서브에이전트가 목표 대비 완성도를 판정하고 미달이면 다시 프롬프트를 넣어 목표까지 자동 도달시킨다. 네 패턴(**턴 기반 · 목표 기반(★) · 시간 기반 · 능동적**)과 무한 루프 방지 중단 조건, 코드 품질·토큰 관리까지.

## 1. 인트로 — 루프의 4가지 패턴 예고 · [0:00](https://youtu.be/VH22y1NMBz4?t=0)
- **3줄 요약**
  - 트위터에서 핫한 '루프 엔지니어링'(클로드 코드 팀 관련)을 발표 경험 바탕으로 설명.
  - 루프의 **네 가지 패턴**을 먼저 다루고, 그 안에서 코드 퀄리티·토큰 관리를 이어서 설명.
  - 시리즈 1편(개론).
- **핵심 인용**: "이 루프에는 지금 한 네 가지 정도의 패턴이 있어요."
- **내 질문**: '프롬프트 엔지니어링'에서 '루프 엔지니어링'으로 무게중심이 옮겨간다는 건, 사람의 역할이 '지시'에서 '검증 설계'로 이동한다는 뜻인가?

## 2. 루프의 정의 — 검증 조건·액션·컨텍스트 · [0:45](https://youtu.be/VH22y1NMBz4?t=45)
- **3줄 요약**
  - 클로드 코드 팀 정의: **"종료 조건이 충족될 때까지 에이전트가 작업 사이클을 반복하는 것"**(공학적 루프와 동일).
  - 구성 요소: **프롬프트 + 검증(종료) 조건 + 액션 + 쌓이는 컨텍스트**.
  - 이 요소들이 돌아가며 **검증 조건에 다다를 때까지** 반복.
- **핵심 인용**: "종료 조건이 충족될 때까지 에이전트가 작업 사이클을 반복하는 걸로 정의를 합니다."
- **내 팁**: 루프의 4요소(프롬프트/검증/액션/컨텍스트)를 분해해 보면 어디를 설계해야 하는지가 보인다 — 대부분은 '검증'이 약하다.

## 3. 왜 루프인가 — "네가 아니라 에이전트가 프롬프트를 치게" · [1:34](https://youtu.be/VH22y1NMBz4?t=94)
- **3줄 요약**
  - 기존 방식: '홈페이지 만들어 줘' → 결과가 별로 → '별로야 다시 해'를 **사람이 목표 도달까지 계속 반복**.
  - 루프 엔지니어링은 이 비효율을 없애라는 것 — **에이전트가 그 반복 프롬프트를 스스로 치게** 만들어라.
  - Excalidraw 그림으로 "목표 도달 위한 사람의 반복 프롬프팅"을 시각화.
- **핵심 인용**: "왜 프롬프트를 계속 쳐? 그거 비효율적이잖아. 너 말고 에이전트가 프롬프트를 치게 해야지."
- **내 질문**: 사람이 하던 '피드백 루프'를 자동화하는 것이므로, 결국 사람의 암묵적 판단 기준을 **명시적 조건으로 외재화**할 수 있느냐가 관건이다.

## 4. 패턴① 턴 기반 루프 — 종료 조건 넣기 · [3:57](https://youtu.be/VH22y1NMBz4?t=237)
- **3줄 요약**
  - **사용자 프롬프트로 트리거**. 핵심은 '홈페이지 만들어 줘'가 아니라 **목적/종료 조건을 처음부터 포함**('여기랑 똑같은 홈페이지').
  - 용도: **짧고 정기적이지 않은 단발성 작업**. 관리는 구체적 프롬프트 + 스킬 MD.
  - 하네스(오마이오픈코드/레이지 코덱스/오마이 코덱스 등)가 **내부적으로 종료 조건을 알아서 생성**해 목표까지 루프.
- **핵심 인용**: "종료 조건을 여러분이 넣어라. 이게 상당히 중요하다."
- **내 팁**: 단발성 작업이라도 종료 조건을 프롬프트에 심으면 '읽고→수정→테스트→재프롬프트'가 자동으로 이어진다.

## 5. 패턴② ★목표 기반 루프★ — 검수관(Evaluator) 서브에이전트 · [6:00](https://youtu.be/VH22y1NMBz4?t=360)
- **3줄 요약**
  - 모든 루프를 이해하는 핵심 패턴. 문제는 **목표가 모호할 때**('비슷하게 만들어 줘'밖에 못 침) — 사용자조차 완수 조건을 못 정의.
  - 해결: 유사도를 **측정 가능한 조건으로 추출**(예: CSS 90% 이상 유사, 색상 유사도 90%). 클로드가 'done' 하는 순간 **검수관 서브에이전트**가 조건 대비 판정.
  - 미달(80%)이면 검수관이 본체에 **"색상 유사도 80% 이하야"를 대신 입력** → 본체가 색을 맞춰 90%로 올림 → 통과 = 루프 1회전. 사람이 프롬프트를 안 쳐도 목표 도달.
- **핵심 인용**: "이 서브에이전트가 (클로드 코드)한테 입력을 해 버립니다. '색깔의 유사도가 지금 80% 이하야.'"
- **내 질문**: 모호한 목표를 정량 조건으로 환원하는 이 단계가 곧 '루프 설계'의 본질 — 정량화가 어려운 '좋음'(카피·톤)은 어떻게 검증 루프에 태울까?

## 6. 중단 조건 & 훅 — 토큰 폭주 방지 · [9:29](https://youtu.be/VH22y1NMBz4?t=569)
- **3줄 요약**
  - 검증관(Evaluator/평가 모델)이 '다시 시도'를 지시 → 목표까지 재시도. 이걸 돌리는 장치가 **훅(hook)**(코덱스·클로드 코드에 훅이 있는 이유).
  - 예: "라이트하우스 점수 90점 이상으로" + **중단 조건("5번/10번 이상 시 중단")**.
  - 중단 조건이 없으면 80→90%를 못 넘고 **무한 반복 → 토큰 소진**. 그래서 최대 시도 횟수를 못박아라.
- **핵심 인용**: "야, 딱 열 번만 해라. 이렇게 적는 거예요."
- **내 팁**: 목표 조건과 **중단(최대 시도) 조건은 항상 쌍**으로. 도달 불가능/기능 고장 시 토큰을 태우지 않는 안전장치.

## 7. 패턴③ 시간 기반 루프 — 스케줄·이벤트 트리거 · [11:32](https://youtu.be/VH22y1NMBz4?t=692)
- **3줄 요약**
  - 앤트로픽 블로그의 **Worker + Validator/Orchestrator를 서브에이전트로 구성**하는 게 앞의 목표 기반 패턴.
  - 시간 기반: **지정된 시간/간격으로 실행**(예: 8:50에 조사 자료 자동 정리, 5분마다 실행). 종료 조건은 작업 완료/취소.
  - 용도: 반복 작업·외부 시스템 연동. 관리는 **긴 간격** 설정, 혹은 **깃허브 리뷰 업로드 등 이벤트 기반** 트리거.
- **핵심 인용**: "지정된 시간 간격으로 클로드 코드를 실행시킬 수 있게 하는 겁니다."
- **내 질문**: 시간 트리거와 이벤트 트리거의 경계 — '9시 실행'과 'PR 올라오면 실행'은 스케줄 vs 이벤트로, 다음 패턴(능동적 루프)과 어떻게 구분되나?

## 8. 패턴④ 능동적 루프 + 코드 품질 + 토큰 관리 · [13:49](https://youtu.be/VH22y1NMBz4?t=829)
- **3줄 요약**
  - **능동적 루프**: 이벤트/스케줄로 트리거 + 목표(예: 리뷰 3개 이상 달 때까지). 모호하면 오작동 → **잘 정의된 반복 작업**만.
  - **코드 품질**: 클로드가 기존 패턴·컨벤션을 따르므로 **깔끔한 코드베이스** + **자체 검증 수단(테스트·린터·포매터)** + 최신 문서 접근성을 제공.
  - **토큰 관리**: 루프가 늘수록 토큰 급증 → **큰 모델은 판단, 작은 모델은 작업**으로 라우팅 + 사용량 코드/대시보드로 모니터링.
- **핵심 인용**: "큰 모델이 판단하는 역할을 하고 작은 모델을 작업하는 데 많이 써라."
- **내 팁**: 검증 수단(테스트/린터)을 붙여야 '좋음'의 주관성을 없애 루프가 자기 점검을 할 수 있다 — 능동적 루프의 전제.

## TL;DR (5줄)

1. **핵심 명제**: 루프 엔지니어링 = 사람이 반복하던 피드백 프롬프트를 **에이전트가 대신 치게** 설계하는 것.
2. **가장 중요한 건 검증 조건 설계**: 모호한 목표('비슷하게')를 **정량 조건(CSS/색상 90% 유사)**으로 추출하는 게 루프 설계의 본질.
3. **목표 기반 루프(★)**: 'done' 시 **검수관 서브에이전트**가 조건 대비 판정 → 미달이면 본체에 자동 재입력 → 목표 도달까지 자동 반복.
4. **네 패턴**: 턴 기반(단발성) · 목표 기반(핵심) · 시간 기반(스케줄/이벤트) · 능동적(이벤트+목표). 앤트로픽의 Worker+Validator/Orchestrator 패턴이 여기 해당.
5. **안전·효율**: 무한 루프·토큰 폭주 방지 위해 **중단(최대 시도) 조건** 필수, 코드베이스 청결+테스트/린터로 자체 검증, 큰 모델=판단/작은 모델=작업 라우팅.
