> 한 줄 요약: 앤트로픽 클로드 코드 팀의 리디아 할리가 공개한 내부 사용법을 다섯 대목으로 옮긴 요약 영상이다. **하루 코드 변경이 지난 5월 2,500건에서 9월 3만 건을 넘겼다**는 수치로 시작해, 모델이 좋아지면서 **연초에 권하던 설정 중에 오히려 성능을 떨어뜨리는 것이 생겼다**는 진단을 전한다. ## 3. 자동 모드가 놓치는 것 — 거부 규칙과 샌드박스 · [01:55](https://youtu.be/pFX8fQFZsfc?t=115)
- **3줄 요약**
  - 자동 모드를 켜 두었는데도 승인 창이 자꾸 뜬다면 **설정부터 보라**고 한다. 믿어도 되는 저장소나 사이트를 평소 말하듯 적어 두면 멈추지 않고 넘어간다는 설명이다. 이어 자동 모드가 위험한 명령을 얼마나 막는지 내부 실험 결과를 전한다 — 코딩 작업 중인 참가자에게 승인 요청 하나를 누가 봐도 위험한 명령으로 슬쩍 바꿔 보냈더니 **사람은 14%만, 자동 모드는 89%를 막았다**고 한다. 그래도 **열 개 중 하나는 그냥 지나간 셈**이다.
  - 그래서 절대 하면 안 되는 일은 **거부 규칙에 적어 두라**고 한다. 예를 들어 API 키나 비밀번호를 모아 둔 `.env` 파일은 자동 모드가 기본으로는 그냥 읽게 되어 있어, 한 번 열면 키가 대화 기록에 그대로 남는다. 거부 규칙에 넣으면 **자동 모드가 판단하기도 전에 막힌다.**
  - 다만 거부 규칙이 보는 것은 **클로드가 치는 명령뿐**이다. `npm test` 로 테스트를 돌리면 그 안에서 남이 만든 패키지 코드도 함께 돌고, 그중 하나가 악성이면 같은 파일을 열어 낯선 서버로 보낼 수 있다. 그래서 **샌드박스도 같이 켜라**고 한다 — 켜면 거부 규칙이 운영 체제에도 넘어가 테스트 도중 어떤 코드가 열려고 해도 운영 체제가 막고, 허락하지 않은 서버에도 접속하지 못한다. 몇 시간씩 걸리는 일은 내 컴퓨터가 아니라 **앤트로픽 서버에서 도는 클라우드 세션**에 맡기면 저장소만 새로 받아 일하므로 내 컴퓨터의 키가 따라가지 않는다.
- **핵심 인용**: "클라우드가 한 번 열면 키가 대화 기록에 그대로 남습니다. 이 파일을 거부 규칙에 넣어두면 자동 모드가 판단하기도 전에 막혀서 클라우드가 아예 열지 못한다고 합니다."
- **내 팁**: 거부 규칙과 샌드박스가 **왜 둘 다 필요한지**가 이 장의 핵심이다. 하나는 클로드가 치는 명령을, 다른 하나는 그 명령이 불러온 남의 코드를 막는다. 둘 중 하나만 켜면 막히는 범위가 반쪽이다.

## 4. 결과는 누가 확인하나 — 테스트·훅·CI·코드 리뷰 · [03:50](https://youtu.be/pFX8fQFZsfc?t=230)
- **3줄 요약**
  - 안전하게 돌아간다고 끝이 아니라 **일을 제대로 했는지도 확인해야 한다.** 기존 로그인 기능을 새 API로 바꾸라고 똑같이 시켜도 어떤 때는 예전 API를 그대로 남겨 두고, 어떤 때는 모든 사용자를 로그아웃시킬 수 있다는 예를 든다. 더 큰 문제는 이런 오류가 있어도 **겉으로는 멀쩡하게 끝난 것처럼 보인다**는 점이다.
  - 그래서 앤트로픽은 작업 중간중간 테스트를 돌려 확인하게 했다. 사람은 몇 시간 동안 작성된 코드를 일일이 보는 대신 **테스트 결과를 먼저 확인**한다. 다만 클로드가 그 테스트를 매번 실행한다는 보장이 없으니 **훅**을 쓴다 — 파일을 수정할 때마다 코드 검사를 돌리고, 작업을 끝내려 할 때는 테스트를 실행하도록 걸 수 있다. 여기서 꼭 확인할 것이 **종료 코드**다. 훅이 1로 끝나면 오류가 나도 작업을 막지 못하지만, **2로 끝나면 실패 내용을 전달해 다시 수정하도록** 할 수 있다.
  - 여러 세션이 동시에 코드를 쓴다면 합치기 전에 같은 검사를 거쳐야 하고 그 역할이 **CI**다. 코드 리뷰에도 클로드를 쓰는데, 코드를 쓴 클로드가 아니라 **처음 보는 클로드에게 새로 읽히는 방식**이다. 사람 검토는 위험도로 나눈다 — 문서나 문구처럼 위험이 적은 변경은 자동 검사만 통과하면 합치고, 일반적인 기능 변경은 개발자 한 명, **위험한 변경은 두 명**이 본다.
- **핵심 인용**: "그러니까 클라우드에게 훅을 만들어 달라고 할 때 실패하면 종료 코드 2를 반환하도록 해 달라고 하면 됩니다."
- **내 팁**: 훅을 만들어 달라고 할 때 **실패하면 종료 코드 2를 반환하게 해 달라**는 문장을 요청에 넣는 것이 이 장에서 바로 따라 할 수 있는 한 줄이다. 1로 끝나는 훅은 걸어 둬도 작업을 멈추지 못한다.

## 5. ★페이블 5.2가 오퍼스 5.5를 관리한다★ · [05:52](https://youtu.be/pFX8fQFZsfc?t=352)
- **3줄 요약**
  - 이렇게 자동화해도 사람이 직접 해야 하는 일이 남는데, 바로 **여러 세션을 띄우고 관리하는 일**이다. 리디아도 여러 작업을 동시에 챙기는 게 쉽지 않았고, 특히 세션이 수십 개씩 늘어나면 어느 세션이 무슨 일을 하는지 확인하기 어려웠다고 한다.
  - 그래서 그 관리 업무까지 클로드에게 맡기고 있다며 **아직 베타 단계인 클로드 코드 프로젝트**를 소개한다. 지휘를 맡은 클로드에게 이번 주 할 일을 한꺼번에 알려 주면 알아서 작업을 나누고 **각 작업을 처리할 새 세션까지 띄워 준다.** 그 작업용 세션을 **스레드**라고 부른다.
  - 지휘 세션과 스레드는 역할에 따라 다른 모델을 쓴다. 회사로 치면 지휘 세션이 팀장, 스레드가 실무자다. 팀장은 코드를 직접 쓰기보다 일을 나누고 결과를 확인하는 역할이라 **페이블 5.2**를, 실제 코드를 쓰는 스레드에는 **오퍼스 5.5**를 쓴다. 두 모델은 프로젝트 설정에서 각각 고를 수 있고, 작업 기록이 너무 길어지면 자동으로 정리된다. **예전에는 세션 여덟 개를 띄워 각각 지시했다면 이제는 지휘 세션 하나에만 이야기하면 된다.**
- **핵심 인용**: "작업이 끝나면 오퍼스가 결과를 보고하고 페이블이 테스트를 통과했는지 확인합니다. 문제가 남아 있으면 다시 수정하도록 지시하고 제대로 끝날 때까지 이 과정을 반복하는 거죠."
- **내 질문**: 지휘 세션과 스레드에 **어느 모델을 왜 그 자리에 두는지**는 팀장·실무자 비유까지만 설명된다. 베타 단계라고만 밝히므로 어떤 조건에서 쓸 수 있는지, 비용이 어떻게 달라지는지는 이 영상만으로는 확인되지 않는다.

## 6. 마무리 — 큰 작업 하나를 맡겨 보라 · [07:32](https://youtu.be/pFX8fQFZsfc?t=452)
- **3줄 요약**

  - 직접 경험해 보고 싶다면 **평소보다 훨씬 큰 작업 하나를 맡겨 보라**고 권한다. 다만 시작 전에 자동 검사가 제대로 작동하는지 확인하고, 클로드가 작업할 환경에서 접속할 곳과 필요한 키를 설정해 두어야 한다. 그렇게 맡긴 뒤 **어디서 멈추는지, 어떤 순간에 사람의 도움이 필요한지** 살펴 그 부분을 하나씩 자동화해 나가면 맡길 수 있는 일이 점점 늘어난다.
- **핵심 인용**: "리디아는 직접 경험해 보고 싶다면 평소보다 훨씬 큰 작업 하나를 맡겨 보라고 합니다."
