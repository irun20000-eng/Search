# 루프 엔지니어링 바로 구축하는 법 — ralph-loop 플러그인으로 캘린더 할일앱 자동 개발

> 한 줄 요약: 하네스(에이전트 팀) 위에 **클로드 공식 `ralph-loop` 플러그인**을 얹어, "캘린더 할일앱 만들어줘" 한 마디로 **완료 기준에 도달할 때까지 스스로 프롬프트를 주입하며 반복 개발**하는 루프를 구축하는 실전. 핵심은 **종료(완료) 조건 설계**(자동 검증+QA 클린+기능 체크)와 **max iteration**(무한 루프 방지), PRD 기반 이터레이션, 아키텍트·백엔드·프론트·QA **서브에이전트 교차 검증**. 단일 에이전트 대비 이점 = "완료가 느낌이 아니라 증거 / 교차 검증으로 버그 자가 발견 / 기록이 자산·투명성"(단 비용↑). [[20260708_루프_엔지니어링_완벽_가이드_1]]의 실습 편.

## 1. 하네스 위에 루프 엔진 설치 — ralph-loop · [00:00](https://youtu.be/nzOMsGpckoY?t=0)
- **3줄 요약**
  - 하네스(에이전트 팀)는 세팅됨. 원하는 건 "다 만들 때까지 자기네끼리 도는" **에이전트 루프** → 하네스 위에 루프 엔진을 얹음.
  - `/plugin install ralph-loop`(**클로드 공식 플러그인**) → repository only 레벨 → `/reload-plugins`.
  - 바로 만들지 말고 **Shift+Tab 플랜 모드**로 "계획만 세워 봐"라고 먼저 컨펌.
- **핵심 인용**: "다 만들 때까지 계속 또는 그 에이전트 루프를 만들고 싶은 거란 말이야."
- **내 팁**: 루프 엔진도 바로 실행보다 '플랜 모드로 계획 컨펌' — 앞 영상들의 선계획 습관과 동일.

## 2. ★완료 조건 + 자율성 = 무한 루프 방지★ · [01:59](https://youtu.be/nzOMsGpckoY?t=119)
- **3줄 요약**
  - **완료 기준이 핵심**(안 그러면 루프가 평생 돌아 토큰만 태움 = '무한 루프'). 옵션: 자동 검증(테스트·빌드·타입체크·린트), QA 리포트 클린, 기능 체크리스트(스토리 단위) → 발표자는 셋 다 빡세게.
  - **자율성**: 감독된 반복(5~10회, 라운드 요약) vs 완전 자율(30·50회·오버나잇) → 발표자는 감독된 반복.
  - **max iteration**으로 상한(예: 30회) — AI가 꼬여 계속 에러로 돌 때 강제 종료.
- **핵심 인용**: "루프가 평생 돌아버려요. … 개발계에서도 가장 무서운 게 바로 무한 루프거든요."
- **내 질문**: '완료를 어떻게 증명할 것인가(종료 조건)'가 루프 설계의 본질 — 이건 [[20260708_루프_엔지니어링_완벽_가이드_1]]의 '검증 조건 설계'와 정확히 같은 이야기 아닌가?

## 3. 루프 스킬 + 자기 프롬프트 주입 원리 · [05:31](https://youtu.be/nzOMsGpckoY?t=331)
- **3줄 요약**
  - 실행하면 **루프 스킬**이 세팅됨("루프 돌려줘/완성될 때까지 반복 개발" 하면 발동). 절차: 컨텍스트 확인 → loop 폴더의 **progress 파일(메모리처럼 진행·다음 작업 기록)** → 기동 → 감독 → 종료.
  - 종료 = **3종 게이트**(빌드/테스트·린트·QA 리포트) 다 통과 or max iteration 소진.
  - 루프 원리 = **AI가 스스로 프롬프트를 매 사이클 주입**. 그 원문 프롬프트("완료 기준 충족까지 반복 개발")는 임의 요약·변경 없이 그대로 계속 주입.
- **핵심 인용**: "AI가 자기 스스로 프롬프트를 주입을 하는 거야. … 매 사이클마다 계속 주입이 되는 거예요."
- **내 팁**: progress.md가 '루프의 기억' — 이터레이션이 끊겨도 이어서 작업하게 하는 상태 파일.

## 4. 실전 개발 — PRD + 서브에이전트 병렬 · [08:50](https://youtu.be/nzOMsGpckoY?t=530)
- **3줄 요약**
  - "캘린더 할일앱을 루프 엔지니어링으로 개발해 줘" → **acceptance(PRD)** 자동 생성(캘린더뷰·CRUD·완료 토글 등), 별도 워크스페이스.
  - 하네스에서 **아키텍트→백엔드→프론트엔드→QA** 서브에이전트가 병렬로 작업(메인은 응답 대기). 하네스 세팅은 발표자의 하네스 영상 참고.
  - 이터레이션 단위: AI가 알아서 나누지만, 가장 적절했던 건 **PRD 리스트의 기능 하나 = 이터레이션 하나**. 각 이터레이션 종료 시 **깃 커밋** 권장(롤백·검토).
- **핵심 인용**: "정확히 하나의 기능이 하나의 이터레이션이 되도록 루프 엔지니어링을 다시 작성해 줘."
- **내 질문**: PRD를 AI가 스스로 뽑아 이터레이션 단위로 삼는 건, 요구사항 정의까지 루프 안으로 넣은 것 — 사람은 '완료 기준'만 쥐고 있으면 되는 걸까?

## 5. 결과 + 교차 검증으로 버그 자가 수정 · [14:02](https://youtu.be/nzOMsGpckoY?t=842)
- **3줄 요약**
  - 이터레이션마다 스스로 프롬프트 재주입 → QA 패스 검사 → **타임존 페일** → 아키텍트가 결정을 계약에 반영, QA 재검증 → 에이전트들끼리 대화하며 수정 → 패스.
  - progress.md에 이터레이션별 기록, **최종 23 이터레이션에서 종료**. 테스트: 월/주/일 캘린더, 할일 CRUD, 완료 표시, 알람까지 스스로 구현.
  - "캘린더 할일 만들어줘" 한 마디에 많은 계획을 짜서 쭉 실행 = 루프 엔지니어링의 위력.
- **핵심 인용**: "버그 생긴 거 스스로 잡았네요."
- **내 팁**: 요구를 더 늘리려면 acceptance(PRD)에 할일들을 추가 → 계속 개발이 이어진다.

## 6. ★단일 에이전트 vs 하네스+루프 — 언제 쓰나★ · [17:35](https://youtu.be/nzOMsGpckoY?t=1055)
- **3줄 요약**
  - 겉보기 퀄리티 차이는 크지 않고 하네스+루프는 시간·토큰이 훨씬 더 듦. 그럼에도 쓰는 이유(AI 답변): ① **완료가 '느낌'이 아니라 '증거'** ② **역할 분리 교차 검증으로 버그 자가 발견**(단일은 자기 코드를 흐린 눈으로 봄) ③ **기록이 자산·투명성**(에러·결정 문서화, 블랙박스 탈피).
  - 단점: **비용 큼**(에이전트마다 프롬프트·대화가 많아 토큰 소모).
  - 언제: 1회성 프로토타입·간단한 건 불필요(간단 명령이면 충분). **유지보수·기능 계속 추가·버그 재발**이면 하네스+루프로 추적·문서화·안전한 설계.
- **핵심 인용**: "이 완료 판정이 느낌이 아니라 증거다."
- **내 질문**: '언제 쓰나'의 판단 기준이 곧 '이 프로젝트가 계속 살아갈 것인가'인데, 오버엔지니어링과 필수 인프라의 경계는 어디일까?

## TL;DR (5줄)

1. **구축**: 하네스 위에 `/plugin install ralph-loop`(공식) → 플랜 모드로 계획 컨펌 → 스킬 세팅.
2. **완료 조건(★)**: 자동 검증+QA 클린+기능 체크 = 종료 조건, **max iteration**으로 무한 루프 방지. 루프=AI가 원문 프롬프트를 매 사이클 자기 주입.
3. **실행**: PRD 자동 생성 → 아키텍트·백엔드·프론트·QA **서브에이전트 병렬**, 기능 1개=이터레이션 1개, 이터레이션마다 깃 커밋 권장.
4. **결과**: 타임존 버그를 에이전트들이 교차 검증으로 자가 수정, 23 이터레이션 만에 캘린더 할일앱(CRUD·알람) 완성.
5. **가치·판단(★)**: 단일 대비 '증거 기반 완료·교차 검증·기록 자산'이 이점(비용↑). 1회성엔 불필요, **유지보수·기능 추가·버그 재발** 프로젝트엔 필수.
