# 클로드·코덱스·제미나이를 동시에 제어합니다 | 하네스 멀티 에이전트 2.0

## 2. 기존 시스템의 4가지 문제 · [0:40](https://youtu.be/HNlBFesXiW8?t=40)
- **3줄 요약**
  - ① **왜 클로드 코드가 오케스트레이터여야 하나** — 여러 모델을 서로 비판시키면 클로드의 약점도 드러나고, **딥SWE(DeepSWE) 벤치마크**에서는 GPT-5.5가 오퍼스를 앞서기도 하며, 앤트로픽이 가격 정책을 바꾸면 위험하다 → 벤더에 종속되면 안 된다.
  - ② **비용** — 클로드 코드·코덱스 기본 구독에 제미나이 구독까지 더하면 부담. 안티그래비티 CLI로 제미나이를 무료로 쓸 수 있어 해결, 모델 조합도 조절 가능하게 설계.
  - ③ **벤더 독립성** — 시스템이 클로드 코드/코덱스/안티그래비티 "어디서든" 돌아야 한다. ④ **설치** — 1.0의 수동 파일 준비 방식은 환경 변화에 약함 → 2.0은 플러그인 한 번 설치로 끝.
- **핵심 인용**
- **내 질문**
- 벤더 독립성을 코드 레벨에서 어떻게 보장할까? → 8장 `backend.json` + 디스패처가 답.
- "제미나이를 무료로"가 핵심 비용 절감 포인트인데, 안티그래비티 CLI 제공 정책이 바뀌면 다시 종속 문제가 생기지 않나?

## 3. 기본 용어 정리 — 하네스 · 오케스트레이터 · 워커 · 팬아웃/팬인 · 호출 방식 · [3:53](https://youtu.be/HNlBFesXiW8?t=233)
- **3줄 요약**
  - **하네스(harness)** = 말의 고삐·안장(제어 장치). 제멋대로인 AI라는 "말"을 고삐로 묶어 통제하는 게 하네스 엔지니어링이고, 그 위에 세운 게 이 시스템.
  - **오케스트레이터(지휘자)** = 작업을 쪼개고 누구에게 시킬지 정하고 결과를 합침. **워커(실무 AI)** = 클로드·코덱스·제미나이 등 실제 작업자. **팬아웃** = 한 작업을 여러 워커에 동시 분배 / **팬인** = 결과를 지휘자가 하나로 취합.
  - **워커 호출 3방식**: 내장 호출(같은 벤더 내 서브에이전트), CLI 호출(터미널 명령어), MCP 호출(AI용 USB 포트 같은 표준 규격). 어느 방식인지는 환경마다 다르고 시스템이 알아서 처리. 지휘자는 "켜는 환경"에 따라 바뀐다(클로드 코드→클로드, 코덱스→GPT, 안티그래비티→제미나이).
- **핵심 인용**
- **내 질문**
- MCP가 "AI용 USB 포트"라면, 내장·CLI 호출 대비 어떤 상황에서 MCP를 선택하는 게 유리할까?

## 4. 시연 1 — 클로드 코드에서 MAT 기능 업그레이드 · [6:06](https://youtu.be/HNlBFesXiW8?t=366)
- **3줄 요약**
  - **MAT(Multi-Agent Tracking)** = 이 시스템으로 처음 만든, 워커 호출 상태를 보여주는 모니터링 프로그램. 시스템 자체는 폴더·파일로만 구성돼 별도 관제 프로그램이 필요했다.
  - 클로드 코드 환경에서 플러그인 설치 → "멀티 에이전트 시스템 구성해줘" 한 줄 → 오케스트레이터로 클로드 선택 → 설치 점검 전부 통과.
  - 기능 추가 전에 클로드·코덱스·제미나이에게 동시에 의견을 받고(팬아웃/팬인), 클로드 메인이 구현 → 코덱스 크리틱이 검수해 버그 2개 발견 → 클로드 메인이 워커 2개 병렬로 수정. MAT에 "호출 방식(CLI/MCP/API)" 표시 기능을 추가했다.
- **핵심 인용**
- **내 질문**
- "만든 워커(클로드)와 검수 워커(코덱스)를 다른 벤더로" 분리하는 게 이 시연의 핵심 같은데, 검수 워커가 틀린 지적을 하면 누가 거르나?

## 6. 시연 3 — 안티그래비티에서 AI 의견 종합하기 · [13:21](https://youtu.be/HNlBFesXiW8?t=801)

## 7. 작동 원리 — 같은 시스템, 바뀌는 오케스트레이터 · [15:19](https://youtu.be/HNlBFesXiW8?t=919)
- **3줄 요약**
  - 핵심 원리는 1.0과 동일: 상태를 파일로 저장 → 승인 → 검증 → 컨텍스트 관리. 목적은 모델별 강점(코딩·검수·비전·긴 문서 분석)을 살려 최상의 결과를 뽑는 것.
  - **이번 버전의 핵심**: 지휘자가 특정 벤더에 고정되지 않는다. 같은 플러그인·같은 폴더·같은 명령인데 "켜는 환경"만 바뀌면 지휘자(클로드 오퍼스/GPT-5.5/제미나이)와 워커 구성이 그에 맞게 바뀐다.
  - **검수 원칙**: 검수는 항상 지휘자와 **다른 벤더**가 맡는다(자기 검수 금지). 크리틱 워커는 평균 4~5개 문제를 찾고 원작 워커가 2~3개를 수정. 매 작업마다 모든 워커를 부르지 않고 필요한 워커만 사용자 승인하에 호출.
- **핵심 인용**
- **내 질문**
- "다른 벤더가 검수"는 이 노트를 만드는 우리 워크플로우(작성 ≠ 검수 분리)와 똑같은 철학이다 — 어디까지 자동화하면 사람이 최종 판단만 해도 될까?

## 8. 워커 구성과 호출 방식 · 컨텍스트 엔지니어링 · 가드레일 · 마무리 · [18:09](https://youtu.be/HNlBFesXiW8?t=1089)
- **3줄 요약**
  - **벤더 독립의 비결**: 워커 호출 방식(내장/MCP/CLI/API)의 차이를 `backend.json` 한 곳에 모으고, **디스패처**가 각 워커에 맞는 방식으로 알아서 호출 → 환경마다 최적 연결을 쓰면서 시스템은 동일하게 동작. (제미나이는 안티그래비티 CLI로 무료 사용.)
  - **컨텍스트 엔지니어링 3원칙**: ① 컨텍스트 비대화 방지(`context.md` 1,500자·`brief.md` 1,200자 제한, 긴 코드는 파일 경로로만 전달) ② 필요할 때 필요한 만큼만 꺼내기 ③ 워커 결과는 다른 워커 검수 후 통과. + 브리프는 중요한 목표·제약을 앞, 금지사항을 뒤에(모델은 가운데를 잘 놓침).
  - **가드레일·자기개선**: 모델 호출 전 사용자 명시 승인 강제(과거 코덱스가 무단으로 클로드를 호출해 사용량 소진된 경험), 전 과정 로그·검수 실패 시 재호출. 작업 후 교훈을 `learnings.md`에 적어 다음에 참고. 시스템 자체 수정용으로 `design-basis.md`(왜 이렇게 만들었나)·`system-invariants.md`(수정 시 지킬 규칙)를 분리.
- **핵심 인용**
- **내 질문**
- `context.md` 1,500자 / `brief.md` 1,200자 제한은 어떤 근거로 정한 수치일까(모델 컨텍스트 한계? 경험칙?).
- "호출 전 사용자 승인 강제"는 안전하지만 자동화 효율을 떨어뜨린다 — 신뢰 구간을 두고 일부 자동 승인하는 절충안은 없을까?

## TL;DR (5줄)

1. **하네스 멀티 에이전트 2.0 = 벤더 독립형 멀티 에이전트 시스템** — 클로드 코드/코덱스/안티그래비티 어디서 켜도 같은 플러그인·폴더·명령으로 동작.
2. **"켜는 환경"이 지휘자(오케스트레이터)가 된다** — 클로드 코드→오퍼스, 코덱스→GPT-5.5, 안티그래비티→제미나이. 시스템은 그대로, 지휘자만 바뀐다.
3. **여러 모델이 서로 만들고 서로 검수** — 검수는 항상 다른 벤더가 맡아 자기 검수를 막고, 팬아웃/팬인으로 의견을 분배·종합한다.
4. **상태는 전부 파일로** — `task.md`/`brief.md`/`context.md`/`result.md`/`learnings.md` + `backend.json`·디스패처로 호출 방식을 추상화, 컨텍스트 엔지니어링 3원칙으로 품질 유지.
5. **안전장치** — 모든 모델 호출은 사용자 승인 후, 결과는 검수 통과 후 진행, 전 과정 로그 기록, 교훈은 누적 학습.
