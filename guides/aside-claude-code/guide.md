# Aside를 Claude Code에 붙이기

> 이 가이드는 **Claude Code가 Aside를 도구로 부리게 만드는 것**을 다룬다. 앱 화면이 아니라 터미널 쪽 이야기다. CLI를 깔고, MCP 서버로 등록하고, 두 도구의 쓰임을 가르고, 로그인 뒤에 있는 페이지를 증거로 가져오는 첫 과제를 돌린 뒤, 스킬로 굳혀 팀과 나누기까지 간다. 약 60분.

## 이 가이드로 만들 것

Claude Code 세션 안에서 **"로그인해야 보이는 페이지를 열어 확인해 줘"가 통하는 구성 하나.**

```
  Claude Code (터미널)
      │  MCP
      ▼
  aside mcp  ── 도구 둘: exec · repl
      │
      ▼
  Aside 브라우저 (내가 로그인해 둔 그 프로필)
      │
      ▼
  CI 로그 · 사내 대시보드 · 회원 전용 게시판
```

**끝났을 때 달라지는 것.** Playwright 처럼 새 브라우저를 띄우는 도구로는 Claude Code 가 로그인 벽 앞에서 멈췄다 [10]. 이 구성이 붙으면 로그인해 둔 페이지의 확인을 Claude Code 가 이어서 한다.

## 이 가이드가 다루지 않는 것

앱 설치와 첫 작업은 [[Aside와 Jev 시작하기]], 앱 화면에서 루틴과 메모리로 업무에 붙이는 일은 [[Aside 업무에 붙이기]] 가 맡는다. 여기서는 **Aside 앱이 이미 깔려 있고 쓸 사이트에 로그인이 끝났다**고 보고 시작한다.

## 왜 Claude Code에 Aside를 붙이나

Claude Code에 브라우저를 주는 도구는 이미 여럿 있다. 구글의 Chrome DevTools MCP, Anthropic의 Claude in Chrome, 마이크로소프트의 Playwright MCP 셋을 나란히 놓고 비교한 영상도 있다 [15]. 그중 로그인 동작이 출처로 확인되는 둘을 Aside 와 나란히 놓으면 이렇다. Chrome DevTools MCP 는 이번 조사에서 로그인 동작을 확인하지 못해 표에서 뺐다.

| 구분 | 여는 브라우저 | 이미 로그인한 사이트 | 로그인 화면을 만나면 |
|---|---|---|---|
| Playwright MCP | 새로 띄운 브라우저 [10] | 쓸 수 없다. 로그인이 안 돼 있다 [10] | 해당 없음. 로그인 상태 없이 시작한다 [10] |
| Claude in Chrome | 내 Chrome 에 새 탭을 연다 [17] | 로그인 상태를 공유해 쓸 수 있다 [17] | 멈추고 사람에게 넘긴다 [17] |
| Aside | 에이전트를 내장한 Aside 브라우저 [10] | 로그인해 둔 세션을 그대로 쓴다 [10] | 주소와 접근 정책을 확인한 뒤 자동 입력한다 [10] |

**먼저 짚어 둘 것.** 이미 로그인한 사이트를 Claude Code 에서 쓰는 것 자체는 **Claude Code 의 Chrome 연동으로도 된다** [17]. Gmail·Notion 처럼 로그인해 둔 앱을 API 연결 없이 다루는 것이 공식 문서가 드는 쓰임이다 [17]. 이미 Chrome 을 쓰고 있고 로그인 화면에서 사람이 한 번 손대는 게 괜찮다면, 그쪽이 새로 깔 것이 적다.

그러면 Aside 쪽에는 무엇이 있나. **Claude Code 쪽에서 확인되는 Aside 의 특징은 도구의 모양이다.** 다른 도구에 비슷한 경로가 있는지는 이 가이드가 비교하지 않았다 — 아래는 우열이 아니라 Aside 를 고를 때 무엇을 얻는지다.

- **결정론적 점검을 따로 적을 수 있다.** Aside 는 같은 브라우저를 CLI·MCP·REPL 세 경로로 내놓고 [2], 그중 REPL 은 매번 같은 순서로 같은 것을 보는 결정론적 단계에 쓰라고 공식 도움말이 적는다 [1]. 에이전트에게 맡기는 길과 순서를 내가 적는 길을 한 도구 안에서 고를 수 있다는 뜻이다 — 3단계에서 다룬다.
- **셸과 스킬에서 부를 수 있다.** MCP 뿐 아니라 CLI 가 따로 있고 [2], 그 CLI 를 구동하는 커뮤니티 스킬도 공개돼 있다 [6]. 5단계에서 다룬다.

**로그인 화면을 만났을 때의 동작은 아직 차별점으로 세우지 않는다.** 국내 비교 정리에 따르면 Aside 는 로그인 화면에 닿으면 대상 주소와 접근 정책을 확인한 뒤 자동 입력하고, 저장된 비밀번호 자체는 에이전트에게 건네지 않는다 [10]. 그러나 이것은 Aside 가 **자기 에이전트**를 돌릴 때의 설명이고, MCP 로 부를 때도 같은지는 확인하지 못했다. 보안문자나 2단계 인증이 낀 사이트에서는 어떤지도 모른다 — 같은 국내 설치기 원문에는 **카카오 로그인의 보안문자와 세션 끊김 때문에 자동화가 실패한 기록**이 있다 [7]. 그래서 이 가이드는 세션이 끊기면 사람이 다시 여는 것을 기본 처방으로 둔다(4단계 막히면).

Playwright MCP 와 견주면 차이가 더 뚜렷하다. 국내 사용기 하나는 기존 자동화 도구가 **"빈 브라우저"에서 시작해** 회원 페이지 문 앞에서 멈추고, Aside 는 매일 쓰는 로그인된 브라우저 안에 AI 를 들여놓는다고 적는다 [8]. 한 개발 유튜버는 브라우저를 바꾼 이유를 **Playwright MCP 를 안 쓰게 됐기 때문**이라고 밝히고, 영상 목차에 "갈아탄 진짜 이유는 로그인 세션"이라는 장을 따로 둔다 [12].

**Claude Code 에게 비밀번호가 가나.** 위 자동 입력 설명은 Aside 가 **자기 에이전트에게** 비밀번호를 넘기지 않는다는 것이다 [10]. MCP 로 붙은 Claude Code 에도 같은 경계가 그대로 적용되는지는 이번 조사에서 확인하지 못했다. 확인 전까지는 **비밀번호를 다루는 페이지를 Claude Code 에게 열어 보게 하지 않는 것**을 기본으로 둔다.

## 사전 준비물

| 항목 | 값 | 확인 방법 |
|---|---|---|
| 운영체제 | macOS | 한 실사용 사례가 준비물로 적은 환경이다 [9]. 윈도우에서의 CLI 설치 절차는 이번 조사에서 확인하지 못했다 |
| Aside 앱 | 설치와 로그인 완료 | 쓸 사이트를 앱에서 한 번 열어 로그인 상태를 확인해 둔다 |
| Claude Code | 설치 완료 | 터미널에서 claude 가 실행되면 된다 |
| 계정 | 자동화할 사이트의 계정 | Aside 브라우저 안에서 로그인해 둔다 [9] |
| Git 저장소 | 결과를 쌓을 곳 | 한 사례는 수집 결과를 저장소에 쌓았다 [9] |
| 사전 지식 | MCP가 무엇인지 | 모르면 관련 영상의 입문편을 먼저 본다 [16] |

## 1단계. Aside CLI 설치하기

CLI를 까는 방법은 둘이다.

```
curl -fsSL https://releases.aside.com/install.sh | bash
```

이 명령 문자열은 해외 커뮤니티 저장소가 적은 것이고 [6], 국내 설치기도 터미널 한 줄로 설치하라고 안내한다 [7]. **2026년 9월 30일 조회 기준**이다 — 설치 명령은 바뀔 수 있으니 공식 다운로드 페이지와 한 번 맞대 보고 실행한다. 국내 설치기에 따르면 앱 안에서 설정의 Developers 메뉴로 들어가 버튼 하나로 까는 길도 있다 [7].

설치가 끝나면 **터미널이 aside 명령을 찾는지**부터 본다.

```
which aside
```

경로가 찍히면 된다. 국내 설치기의 예시는 이 경로를 `~/.local/bin/aside` 로 쓴다 [7] — 2단계에서 이 경로가 다시 필요하니 적어 둔다.

**화면에서 확인할 것**: `which aside` 가 빈 줄이 아니라 파일 경로 한 줄을 돌려준다.

**막히면**: 빈 줄이 나오면 설치는 됐는데 셸이 그 폴더를 모르는 경우가 많다. 터미널을 새로 열어 다시 쳐 본다. 그래도 안 나오면 설치 스크립트 출력의 마지막 줄들을 다시 읽는다 — 설치 위치가 거기 찍혀 있다.

## 2단계. Claude Code에 MCP 서버로 등록하기

`aside mcp` 를 실행하면 Aside가 **MCP 서버**가 된다 [1]. Claude Code는 그 서버를 하위 프로세스로 띄워 도구처럼 쓴다. 브라우저처럼 **내 기기의 자원을 써야 하는 도구**가 이 방식에 맞는다고 Claude Code 공식 문서가 적는다 [3].

등록은 한 줄이다.

```
claude mcp add aside -- aside mcp
```

규칙은 이렇다. `--` 뒤에 오는 것 전부가 Claude Code가 실행할 명령이다 [3]. 로컬 서버라 전송 방식 플래그는 붙이지 않는다 [3].

**범위(scope)를 먼저 정한다.** 아무것도 안 붙이면 **이 프로젝트에서만, 나에게만** 보인다 [3]. 모든 프로젝트에서 쓰려면 user, 팀과 나누려면 project다 [3].

```
claude mcp add --scope user aside -- ~/.local/bin/aside mcp
```

경로 `~/.local/bin/aside` 는 국내 설치기의 예시다 [7]. **1단계에서 `which aside` 가 돌려준 경로로 바꿔 넣는다.**

`--scope` 가 `--` **앞에** 있다는 것을 본다. 이 순서는 반드시 지켜야 한다 [11] — 틀렸을 때 무슨 일이 나는지는 「흔히 막히는 지점」 1번에 적었다.

국내 설치기에 따르면 앱 쪽에서도 같은 연결을 걸 수 있다 — Developers 메뉴에서 CLI를 설치한 뒤 스킬 추가 대상으로 Claude Code를 고르고 Aside MCP 서버 토글을 켜는 순서다 [7]. 메뉴 이름은 버전에 따라 다를 수 있으니, 터미널 쪽 명령을 기준으로 삼는 편이 확인하기 쉽다.

**화면에서 확인할 것**: 터미널에서 `claude mcp list` 를 치면 aside 가 목록에 있다 [4]. Claude Code 세션 안에서 `/mcp` 를 열어도 같은 서버가 보인다 [4].

**막히면**: 목록에는 있는데 연결이 실패로 나오면 흔한 원인은 Claude Code 가 aside 명령을 못 찾는 것이다. 1단계에서 본 **절대 경로**로 다시 등록한다. 같은 이름이 이미 있으니 먼저 `claude mcp remove aside` 로 지운 뒤 [4] 다시 추가한다.

## 3단계. exec와 repl 가르기

국내 설치기에 따르면 `aside mcp` 가 Claude Code 에 내미는 도구는 **둘**이다 — `exec` 와 `repl` [7]. 이름이 비슷해 보여도 쓰임이 다르다.

| 도구 | 누가 판단하나 | 언제 쓰나 |
|---|---|---|
| exec | Aside 의 에이전트에게 일을 넘긴다. CLI 는 실제 로그인 프로필로 그 에이전트를 돌린다 [6] | 일의 결과가 필요할 때 |
| repl | 내가 적은 단계를 그대로 실행한다 | 페이지를 직접 들여다보거나, 스크린샷·내려받기처럼 매번 똑같아야 하는 단계일 때 [1] |

도움말 요약에 나온 repl 예는 이렇다 [1].

```
aside repl "const p = await openTab('https://example.com')"
```

공식 개발자 안내는 셋의 쓰임을 이렇게 가른다 — 브라우저 확인이 개발 흐름 안에 들어가야 하면 **CLI**, 코딩 에이전트가 사설 페이지의 증거를 가져와야 하면 **MCP**, 결정론적으로 들여다봐야 하면 **REPL** [2].

**판별 한 줄.** "결과만 맞으면 된다"면 exec, "매번 같은 순서로 같은 것을 봐야 한다"면 repl 이다. REPL 이 결정론적 단계용으로 따로 있는 만큼 [1][2], exec 에는 **결과가 매번 같은 길로 나온다고 기대하지 않는 편이 안전하다.** 테스트 확인이나 캡처처럼 재현성이 가치인 일은 repl 로 적는다.

**화면에서 확인할 것**: Claude Code에게 "aside 도구 목록을 보여 줘"라고 하면 exec 와 repl 두 이름이 나온다.

**막히면**: 한쪽만 보이면 서버가 오래된 설정으로 붙어 있는 것일 수 있다. `/mcp` 에서 aside 를 다시 연결하거나, 2단계의 지우고 다시 추가하기를 한 번 더 한다.

## 4단계. 첫 과제 — 로그인 뒤의 증거 가져오기

공식 개발자 안내가 MCP의 쓰임으로 드는 예가 곧 첫 과제로 좋다 — **CI 로그나 기능 플래그 대시보드처럼 사설 페이지에 있는 증거**를 코딩 에이전트가 직접 가져오는 것이다 [2].

Claude Code 세션에서 이렇게 시킨다.

```
  "aside 로 우리 CI 대시보드를 열어서 main 브랜치의 마지막 실패 빌드를 찾고,
   실패한 스텝 이름과 에러 메시지 첫 20줄을 가져와.
   그다음 이 저장소에서 그 에러가 난 파일을 찾아 원인을 추정하고,
   가져온 원문과 추정을 evidence/ci-<오늘 날짜>.md 로 저장해 줘."
```

이 지시가 좋은 이유는 **증거 수집과 판단을 한 세션 안에서 잇는다**는 데 있다. 예전 같으면 사람이 대시보드에 들어가 로그를 복사해 붙여 넣어야 했다. 지금은 Claude Code가 브라우저에서 가져온 것을 바로 코드와 맞대 본다.

지시를 쓸 때 지킬 것 둘.

1. **가져올 것의 양을 정한다.** "로그 전부"가 아니라 "첫 20줄". 로그인된 페이지의 내용은 전부 Claude Code의 문맥으로 들어온다. 많이 가져올수록 비싸고 느리다 — 개발 유튜버 한 명은 이 도구의 **토큰 효율을 직접 재 본** 장을 영상에 따로 두었다 [12].
2. **결과를 파일로 남기게 한다.** 사람이 나중에 확인할 수 있어야 한다. 사전 준비물에 Git 저장소를 넣은 것이 이 때문이다.

**화면에서 확인할 것**: Claude Code의 응답에 **대시보드에서만 볼 수 있는 값**(빌드 번호, 실패 시각, 스텝 이름)이 들어 있다. 그 값을 브라우저에서 직접 열어 한 번 맞대 본다.

**막히면**: Claude Code 가 대시보드 값 대신 **로그인 화면의 문구**(아이디·비밀번호 입력란, "다시 로그인" 안내)를 결과로 들고 왔다면, 도구는 정상이고 가져온 페이지가 틀린 것이다. 저장된 evidence 파일을 열어 첫 줄을 보면 바로 가려진다. 그 사이트를 Aside 브라우저에서 한 번 열어 로그인 상태를 되살린 뒤 같은 지시를 보낸다.

## 5단계. 스킬로 굳히기

4단계가 두 번 통하면 **스킬**로 만든다. Claude Code의 스킬은 `SKILL.md` 파일 하나가 중심인 디렉터리이고, **디렉터리 이름(앞머리에 name 을 적었으면 그 이름)이 곧 내가 칠 명령**이 된다 [5]. 개인 스킬은 `~/.claude/skills/`, 프로젝트 스킬은 저장소 안 `.claude/skills/` 에 둔다 [5].

```
  ~/.claude/skills/
    ci-evidence/
      SKILL.md        ← 무엇을, 어떤 순서로, 얼마만큼 가져올지
```

이렇게 두면 `/ci-evidence` 로 부를 수 있다. 스킬 앞머리의 description 은 **Claude가 이 스킬을 알아서 꺼낼지 판단하는 근거**가 된다 [5] — 여기에 "CI 실패 원인을 볼 때"처럼 부르는 상황을 적어 두면 명령을 안 쳐도 쓰인다.

Aside 쪽 커뮤니티에서도 같은 방식의 스킬 디렉터리를 만들어 `~/.claude/skills/` 에 복사해 쓰는 예가 공개돼 있다 [6]. 남이 만든 스킬을 가져다 쓸 때는 **SKILL.md 를 먼저 끝까지 읽는다** — 그 파일이 곧 Claude Code에게 줄 지시다.

**스킬이 셸에서 CLI 를 부르는 경우의 함정.** 그 커뮤니티 스킬처럼 MCP 가 아니라 **CLI 를 구동하는** 구성이라면 [6] 하나를 알아 둔다. 그 저장소의 기록에 따르면 비대화형으로 도는 `aside exec` 는 **권한 확인이나 질문에 답할 수 없어**, 1.26.831 버전까지는 이런 상황에서 끝없이 기다렸고 1.26.902 버전부터는 **호출을 거부하고 종료 코드 0 으로 넘어간다** [6]. 공식 문서로 교차 확인하지 못한 한 자료의 기록이고, **MCP 도구로 부를 때도 같은지는 확인하지 못했다.** 그래도 CLI 경로라면 뜻이 크다 — **종료 코드 0 이 성공을 뜻하지 않는다.** 스킬에 「결과 파일에 기대한 값이 들어 있는지 확인하라」를 한 줄 넣어 둔다.

**화면에서 확인할 것**: 스킬을 만든 그 세션에서 `/` 를 쳤을 때 내가 만든 스킬 이름이 목록에 나온다.

**막히면**: 이미 있던 skills 디렉터리 안의 변경은 재시작 없이 반영된다 [5]. 그런데도 안 보이면 **세션을 시작할 때 그 최상위 skills 디렉터리가 없었던** 경우다 — 공식 문서는 이때 `/reload-skills` 를 치라고 적는다 [5]. 새 세션에서도 안 보이면 SKILL.md 의 위치(디렉터리 한 단계 안인가)와 앞머리를 먼저 본다.

## 6단계. 팀과 나누고 경계 긋기

혼자 쓰던 구성을 팀에 넘기려면 범위를 **project** 로 등록한다.

```
claude mcp add --scope project aside -- aside mcp
```

그러면 설정이 저장소 루트의 `.mcp.json` 에 적히고, 이 파일을 커밋하면 저장소를 받은 팀원이 Claude Code를 열 때 **이 서버를 승인할지 묻는 창**을 받는다 [3]. 파일 모양은 이렇다 [1][7].

```
{
  "mcpServers": {
    "aside": {
      "command": "aside",
      "args": ["mcp"]
    }
  }
}
```

**승인 창을 가볍게 넘기지 않는다.** 이 서버가 여는 것은 **그 팀원 자신이 로그인해 둔 브라우저**다. 같은 설정이라도 사람마다 열리는 계정이 다르다.

여기 명령은 경로 없이 `aside` 만 적었다. `.mcp.json` 은 팀원 모두가 쓰는 파일이라, 한 사람의 절대 경로를 넣으면 다른 사람의 기기에서 맞지 않기 때문이다.

**화면에서 확인할 것**: 저장소 루트에 `.mcp.json` 이 생겼다. `.mcp.json` 을 **커밋한 뒤** 이 저장소를 다른 폴더에 새로 클론해 Claude Code 를 열면 aside 서버를 승인할지 묻는 창이 뜨고, 승인 뒤 `/mcp` 에 aside 가 보인다. 공식 문서가 명시한 동작은 팀원이 받는 승인 창까지이고 [3], 이 방법은 혼자서 팀원 입장을 흉내 내는 것이다.

**막히면**: 팀원 쪽에서 연결이 실패하면 흔한 원인은 그 사람의 기기에 CLI 가 없거나 셸이 aside 를 못 찾는 것이다. `.mcp.json` 은 명령 이름만 담으므로 **CLI 설치는 각자 해야 한다.** 설치했는데도 못 찾으면 그 팀원만 **다른 이름으로** local 범위에 절대 경로를 따로 등록해 쓴다 — 예를 들어 `claude mcp add aside-local -- <그 사람의 aside 경로> mcp`. local 은 그 사람에게만 적용된다 [3]. 같은 이름 aside 로 겹쳐 등록했을 때 어느 쪽이 이기는지는 이번 조사에서 확인하지 못해 이름을 가른다. 1단계를 팀 온보딩 문서에 넣어 둔다.

## 실제 사례 — 로그인 벽 뒤에서 2,428건

이 구성이 실제로 어디까지 가는지 보여 주는 국내 사례가 있다 [9]. 커뮤니티를 조사하려는데 사람들이 진짜 이야기를 하는 곳은 **죄다 로그인 벽 뒤**에 있었다 — 페이스북 그룹, 레딧, 대학 커뮤니티 같은 곳이다 [9]. 작성자는 Aside를 Claude Code에 붙여 이 문제를 풀었고, **2,428건의 커뮤니티 목소리와 1,436명의 서로 다른 사람**의 데이터를 모았다고 밝힌다 [9].

그 글의 표현이 이 구성의 성격을 잘 요약한다 — **Claude Code가 Aside를 인턴처럼 부린다** [9]. Claude Code가 무엇을 모을지 정하고 순서를 짜면, Aside가 로그인된 브라우저에서 실제로 들어가 가져온다. 준비물도 이 가이드와 같다 — macOS, Aside 앱, Claude Code, 로그인해 둘 계정, 결과를 쌓을 Git 저장소 [9].

**이 사례에서 가져갈 것은 규모보다 구조다.** 결과를 저장소에 쌓도록 짜 두면 [9], 다시 돌려도 이어서 쌓이고 무엇을 언제 모았는지가 커밋으로 남는다.

## 흔히 막히는 지점

**1. `--` 뒤에 Claude Code 플래그를 붙인다.**
`--scope`, `--env`, `--transport`, `--header` 같은 Claude Code 쪽 플래그는 **반드시 `--` 앞에** 와야 한다 [11]. `--` 뒤에 쓰면 그것은 Claude Code의 설정이 아니라 **aside 명령에 넘어가는 인자**가 된다 [3]. 등록은 성공한 것처럼 보이는데 범위가 기본값으로 잡혀 있어, 다른 프로젝트에서 "서버가 없다"고 나온다.

**2. 나중에 범위만 바꾸려 한다.**
범위는 등록할 때 고정된다. 바꾸려면 지우고 새 범위로 다시 추가해야 한다 [3]. 처음부터 "이걸 다른 프로젝트에서도 쓸까"를 정하고 등록하면 한 번에 끝난다.

**3. 스킬이 셸에서 부른 CLI 의 종료 코드 0을 성공으로 읽는다.**
5단계에서 본 것처럼, 커뮤니티 기록상 셸에서 부른 비대화형 `aside exec` 는 권한 질문을 만나면 **거부하고 0으로 끝날 수 있다** [6]. 그러면 스킬은 명령이 성공했다고 보고 다음 단계로 넘어간다. **가져온 값이 실제로 들어 있는지**를 봐야 하고, 스킬이 남긴 결과 파일이 비어 있거나 로그인 화면 문구만 있으면 그게 신호다. MCP 도구로 부를 때도 같은지는 확인하지 못했다.

**4. 재현이 필요한 확인을 exec 로 시킨다.**
exec 는 일을 에이전트에게 넘기는 도구라 [6], 결정론적 단계용으로 따로 둔 REPL 과 달리 [1][2] 매번 같은 길로 간다는 보장을 기대하기 어렵다. 캡처·내려받기·정해진 순서의 점검처럼 **같아야 하는 일**은 repl 로 적는다 [1]. 3단계의 판별 한 줄로 되돌아간다.

**5. 로그인된 페이지의 내용을 믿을 만한 입력으로 다룬다.**
Aside가 가져온 페이지 내용은 그대로 Claude Code의 문맥이 된다. 그 페이지에 **남이 쓴 글**이 섞여 있다면 그것도 함께 들어온다는 뜻이다. 개발 유튜버 한 명도 영상에서 보안과 프롬프트 인젝션, 권한 모드를 따로 장으로 둔다 [12]. **커뮤니티처럼 남이 쓴 글을 모으는 작업은 결과를 읽기만 하게 하고, 그 결과로 무언가를 실행하게 하지 않는다.**

**6. 스킬을 만들고 SKILL.md 를 안 다시 읽는다.**
스킬은 한 번 만들면 명령 하나로 반복된다. 처음 적은 "가져올 양"이 너무 많았다면 **그 과잉도 매번 반복된다.** 두세 번 돌린 뒤 결과를 보고 SKILL.md 의 양과 순서를 한 번 줄인다.

## 다음으로 할 것

- **팀원 한 명에게 직접 받아 보게 한다.** 6단계에서 혼자 재현한 승인 창을 실제 팀원이 받는지, 그 사람의 기기에서 aside 가 잡히는지 확인한다. 안 잡히면 6단계 막히면의 local 범위 처방을 넘긴다.
- **스킬을 하나 더 만든다.** CI 증거 다음으로 흔한 것은 사내 대시보드의 숫자를 가져와 코드 변경과 맞대는 일이다. 4단계와 같은 틀에 대상만 바꾼다.
- **repl 로 점검 목록을 적는다.** 배포 뒤 확인할 화면 서너 개를 repl 명령으로 적어 두면, 매번 같은 순서로 같은 것을 본다 [1].
- **앱 쪽 기능과 겹쳐 쓴다.** 루틴과 메모리는 앱 화면에서 다루는 편이 쉽다 — [[Aside 업무에 붙이기]] 가 그쪽을 단계로 잡아 뒀다.
- **모으는 일과 가르는 일을 떼어 놓는다.** 2,428건 사례처럼 수집이 커지면 [9], 한 세션이 가져오기와 분류를 다 맡을 때 문맥이 금방 찬다. 수집은 Aside 가 저장소에 쌓고 분류는 그 파일을 읽는 **별도 세션**이 맡게 나누면, 분류 기준을 바꿔도 다시 모을 필요가 없다. 확률로 가르는 판단 모델까지 붙일 생각이면 [[Jev와 Aside]] 보고서가 그 배경을 다룬다.
