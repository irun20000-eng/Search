# Aside 업무에 붙이기

> 이 가이드는 **Aside를 이미 설치해 본 사람이 그것을 실제 업무에 붙이는 것**을 다룬다. 활용 예시를 지도로 펼치고, 시간이 어디서 나오는지 계산하고, 2주치 실천 과제로 끝낸다. 약 90분.

## 이 가이드로 만들 것

2주 뒤에 **"이 일은 이제 Aside가 한다"고 말할 수 있는 업무 한 개**를 만든다.

```
[1단계] 붙일 일 고르기      →  후보 3개 중 1개 확정
[2단계] 읽기로 첫 성과       →  여러 화면을 한 장으로
[3단계] 메모리 읽고 고치기    →  틀린 기억을 먼저 잡는다
[4단계] 루틴으로 예약        →  내가 안 열어도 돈다
[5단계] 브라우저 밖에서 부르기 →  슬랙·터미널에서 지시
[6단계] 비용 0으로 고정      →  내 구독을 연결
```

**왜 이 순서인가.** 읽기는 실패해도 되돌릴 수 있고, 쓰기는 아니다. 그래서 신뢰를 쌓는 순서대로 간다. 루틴을 1단계에 놓으면 **검증 안 된 작업이 매일 아침 자동으로 돌아간다.**

## 이 가이드가 다루지 않는 것

설치·데이터 임포트·비밀번호 이전·첫 작업은 **[[Aside와 Jev 시작하기]]** 가 단계로 잡아 뒀다. 여기서는 그것이 끝났다고 보고 시작한다. Jev도 다루지 않는다 — 별개 제품이고 그쪽 가이드에 있다.

## 사전 준비물

| 항목 | 값 | 확인 방법 |
|---|---|---|
| Aside | 설치 후 첫 작업 1회 완주 | 작업 기록에 완료된 항목이 하나라도 있으면 된다 |
| 후보 업무 | 매주 2회 이상 반복하는 웹 업무 | 아래 1단계의 세 조건으로 고른다 |
| 모델 구독 | 클로드 또는 ChatGPT 또는 GitHub Copilot 중 하나 | 이미 내고 있는 것을 연결한다 [8] |
| 기록할 곳 | 메모 앱이나 스프레드시트 | 실측 시간을 적어야 효율을 계산할 수 있다 |
| 시간 | 90분 + 2주간 하루 10분 | 실천 과제가 2주짜리다 |

⚠️ **먼저 정해 둘 것.** 이 2주 동안 **결제·발송·게시는 Aside에 맡기지 않는다.** Aside는 그런 민감한 작업에서 사용자 확인을 기다리도록 설계돼 있지만 [1], 확인 단추를 습관적으로 누르기 시작하면 그 설계가 무력해진다. 읽기와 정리로 신뢰를 먼저 만든다.

## 활용 지도 — Aside가 어디에 붙나

공식 문서가 직무별로 활용을 갈라 놓았다 [1]. 자기 일에서 가장 가까운 줄부터 읽으면 된다.

⚠️ **아래 표의 근거는 공식 페이지 하나다.** 프록시 차단으로 원문을 직접 열지 못해 검색 요약으로 재구성했으니, 항목 이름은 실제 화면과 다를 수 있다. 활용의 **방향**을 보는 용도로 읽을 것.

| 직무 | 붙는 일 | 왜 여기가 되나 |
|---|---|---|
| 인사 | 온보딩·오프보딩, 채용 진행, 복리후생 점검 | 사내 포털이 API를 안 준다 |
| 재무·구매 | SaaS 리포팅, 갱신 점검, 인보이스 내려받기, 승인 처리 | 로그인해야 보이는 화면이 대부분이다 |
| 리서치·준법 | 출처 수집, 주장 검증, 가격 페이지 캡처, PDF 필드 추출 | 증빙을 남기며 여러 페이지를 훑어야 한다 |
| 영업 | 콜 사전조사, CRM 필드 검증, 후속 자료 정리, 후보 목록 만들기 | CRM과 외부 사이트를 오간다 |
| 개발 | CI 결과 분류, 대시보드 감시, 릴리스 증빙 수집 | 채팅·CLI·MCP에서 브라우저를 부를 수 있다 [7] |

국내 사용기들이 실제로 든 예도 결이 같다 — 쇼핑몰 장바구니와 결제 내역 확인, 인스타그램 인플루언서 조사 [17], 썸네일 제작과 구독료 점검과 YouTube Studio 분석 [16], 블로그 글 준비와 발행 [9]. **공통점은 "로그인해야 보이는 화면을 여러 개 오가는 일"이다** [10]. 열 가지를 직접 해 본 국내 기록도 같은 결론을 낸다 — 로그인된 브라우저 작업·리뷰 작성·폼 입력·자료 비교·루틴과 CLI 를 훑어 본 끝에, **이미 로그인된 브라우저에서 다음 작업을 이어 맡길 때 가장 유용하다**고 정리한다 [6].

특이한 활용이 나오는 자리는 대체로 같은 성질을 갖는다 — **API 가 없는 관리자 페이지, 오래된 내부 도구, 복잡한 SaaS 설정 화면, 사람이 매번 클릭해야 하는 포털 업무** [13]. 1인 창업자를 대상으로 쓴 국내 운영법 글이 드는 예도 이 성질에 모여 있다 [13].

> **한 줄 판별법**: 그 일을 남에게 시키려면 **내 계정을 빌려줘야 하는가.** 그렇다면 Aside 자리다. API 키만 주면 되는 일은 기존 자동화 도구가 더 안전하고 싸다.

## 1단계. 붙일 일 고르기

여기서 잘못 고르면 뒤 다섯 단계가 다 헛수고다. 국내 정리글이 제시한 **두 조건**에 하나를 더해 쓴다 [12].

```
  조건 1  대상이 분명한가    특정 메일함, 정해진 페이지, 시트의 지정 범위
  조건 2  반복되는가        매주 같은 비교, 매일 새 문의 정리
  조건 3  되돌릴 수 있는가   틀려도 읽기·초안이라 피해가 없다   ← 이 가이드가 추가하는 조건
```

**후보를 셋 적고 하나만 고른다.** 셋을 동시에 시작하면 무엇이 효과가 있었는지 못 가린다.

그리고 **지금 그 일에 걸리는 시간을 스톱워치로 재 둔다.** 이 숫자가 없으면 뒤에서 효율을 계산할 수 없고, 기억으로 적으면 대체로 부풀려진다.

**화면에서 확인할 것**: 메모에 후보 3개와 각각의 실측 소요 시간(분)이 적혀 있고, 그중 하나에 동그라미가 쳐져 있다.

**막히면**: 후보가 안 떠오르면 브라우저 방문 기록을 어제치만 훑어본다. **같은 사이트를 하루에 세 번 이상 열었다면 그게 후보다.** 한 국내 사용 후기에 따르면 루틴 화면에 반복 작업을 훑어 찾아 주는 기능이 있다고 하니 그것도 열어 본다 [14].

## 2단계. 읽기 작업으로 첫 성과 만들기

첫 작업은 **여러 화면을 하나로 합치는 일**로 잡는다. Aside가 기존 도구와 갈리는 지점이 여기서 가장 잘 보인다 — 연동을 붙이지 않고 내가 로그인해 둔 사이트를 그대로 연다 [1][10].

이런 식으로 시킨다.

```
  "결제 내역 페이지, 구독 관리 페이지, 카드 명세 페이지를 열어서
   이번 달에 빠져나간 정기결제를 한 표로 만들어 줘.
   서비스명, 금액, 결제일, 다음 결제일 네 칸으로."
```

요청을 쓸 때 지키면 결과가 확 좋아지는 두 가지가 있다.

1. **출력 형태를 지정한다.** "정리해 줘"가 아니라 "네 칸 표로". 형태를 안 주면 매번 다른 모양이 나와 다음 단계에서 못 쓴다.
2. **범위를 좁게 자른다.** "전체"가 아니라 "이번 달". 무료 플랜은 월 500 크레딧이라 큰 작업을 반복하면 금방 닳는다 [4][5].

여러 출처를 오래 훑어야 하는 조사라면 **Ultrabrowse** 쪽이 맞다 — 공식 도움말은 계획이 더 필요한 작업과 페이지 간 비교에 쓰는 모드라고 적는다 [2].

**화면에서 확인할 것**: 결과가 **내가 지정한 칸 수의 표**로 나오고, 그 표를 스프레드시트에 그대로 붙일 수 있다. 붙여서 칸이 안 맞으면 다음 주에 이 지시를 재사용할 수 없다는 뜻이니 형태 지정을 고쳐 다시 시킨다.

**막히면**: 세 화면 중 한 곳만 비어 나오면 그 사이트의 세션이 끊긴 것이다. **어느 화면이 비었는지를 먼저 적어 둔다** — 매번 같은 곳이 빈다면 그 사이트는 이 업무에서 빼고 나머지로 자동화 범위를 다시 그리는 편이 빠르다. **로그인에 보안문자가 끼는 사이트는 자동화 자체가 막히는 사례가 보고돼 있다** [11].

## 3단계. 메모리를 읽고 고치기

**메모리가 무엇이고 어떻게 쌓이는지는 [[Aside와 Jev 시작하기]] 가 다룬다.** 이 단계가 다루는 것은 하나다 — **쌓인 것을 사람이 열어서 고치는 일.**

이게 별도 단계인 이유가 있다. 메모리는 편집 가능한 로컬 파일로 남아 사람이 읽고 고칠 수 있고 [3], 한 번 실수한 작업을 기억해 다음엔 같은 실수를 피하는 구조라고 알려져 있다 [14]. 두 성질을 겹쳐 놓으면 결론이 하나 나온다 — **틀린 기억도 같은 방식으로 굳는다.** 자동화를 얹기 전에 기억을 한 번은 교정해야 하는 것이 이 때문이다.

순서가 중요하다.

```
  ① 메모리를 열어 2단계가 남긴 항목을 읽는다
  ② 틀린 항목을 고친다                        ← 여기까지 하고
  ③ 같은 일을 지시문 절반으로 다시 시킨다      ← 그 다음에 이것
```

②와 ③을 바꾸면 **틀린 기억 위에서 두 번째 시도를 하게 되고**, 결과가 나빠도 원인이 지시문인지 기억인지 못 가린다.

고칠 때 볼 것은 **고유명사**다. 회사명·서비스명·담당자명이 잘못 들어가 있으면 다음 작업이 엉뚱한 페이지를 연다. 형용사나 요약문은 틀려도 피해가 작다.

**화면에서 확인할 것**: 내가 고친 항목이 저장된 뒤, 지시문을 절반으로 줄인 세 번째 요청에서도 **결과 형태가 유지된다.** 형태가 흐트러지면 아직 지시문이 메모리보다 많은 일을 하고 있는 것이다.

**막히면**: 메모리에서 고칠 항목을 못 찾겠으면 아직 고칠 단계가 아니다. 2단계를 종류가 다른 업무로 한 번 더 돌려 항목을 늘린 뒤에 열어 본다.

## 4단계. 루틴으로 반복을 없애기

여기가 이 가이드의 본론이다. **같은 일을 두 번 성공시켰으면 예약한다.** 루틴은 "매일 아침 9시에 이 페이지 확인해서 달라진 것만 알려 줘" 같은 예약을 브라우저 안에 걸어 둔다 [8][11].

```
  루틴을 걸기 전 체크
  ├ 같은 지시로 두 번 이상 성공했는가
  ├ 실패해도 피해가 없는가 (읽기·초안인가)
  └ 결과를 내가 매번 볼 자리가 있는가
```

**세 번째가 자주 빠진다.** 아무도 안 보는 루틴은 조용히 틀리다가 어느 날 문제가 된다.

루틴을 쓸 때 실전에서 갈린 대목이 하나 있다 — **만드는 단계와 실제로 제출·실행하는 단계를 갈라 두는 것**이다 [11]. 생성까지만 루틴이 하고 제출은 사람이 누르게 하면, 루틴이 틀려도 밖으로 안 나간다.

무료 플랜에서 루틴을 여러 개 굴리려면 용량이 부족할 수 있다. 무제한 루틴과 원격 조종은 Pro 구간의 기능이다 [5].

**화면에서 확인할 것**: 루틴 목록에 내가 만든 항목이 있고 **다음 실행 시각**이 표시된다. 하루를 기다린 뒤 결과물이 실제로 도착했는지 본다.

**막히면**: 예약 시각이 지났는데 아무 일도 없으면 브라우저가 그 시각에 꺼져 있었을 가능성이 크다. Aside는 내 기기에 설치해 쓰는 브라우저다 [5]. 기기를 켜 두기 어렵다면 그 일은 루틴으로 안 맞는 일이다.

## 5단계. 브라우저 밖에서 부르기

업무에 진짜로 붙는 순간은 **브라우저를 열지 않고도 시킬 수 있게 될 때**다. 두 경로가 있다.

- **Channels** — 슬랙·텔레그램 같은 메신저에서 원격으로 지시한다. Pro 구간 기능이다 [5].
- **CLI·MCP** — 터미널에서 자연어로 브라우저를 움직인다 [7]. 코딩 에이전트가 Aside를 브라우저 실행 도구로 쓰는 구성도 여기서 나온다 [7].

개발 쪽에서 체감이 큰 대목이 이것이다. 한 리뷰어는 **Playwright MCP를 더 안 쓰게 됐다**는 것을 브라우저를 바꾼 이유로 든다 [19]. 테스트용 브라우저를 따로 띄우지 않고 이미 로그인된 브라우저를 그대로 쓰기 때문이다.

**화면에서 확인할 것**: 브라우저 창을 앞으로 가져오지 않은 상태에서 지시를 보냈고, 결과가 메신저나 터미널로 돌아왔다.

**막히면**: CLI가 엉뚱한 폴더를 보는 일이 흔하다. **CLI 실행 폴더와 Aside 프로젝트 작업 폴더가 자동으로 일치하지 않는다**는 보고가 있다 [11] — 경로를 명시해 주면 풀린다.

## 6단계. 비용을 0으로 고정하기

마지막은 돈 문제다. 결론부터 적으면 **이미 내고 있는 AI 구독이 있으면 Aside는 추가 지출 없이 쓸 수 있다.**

핵심은 크레딧이 어떻게 닳는지다. **한 국내 사용기는 크레딧이 Aside 자체 모델을 쓸 때만 줄어든다고 적는다** [8] — 공식 요금 문서를 직접 열지 못해 이 한 자료에 의존하는 대목이니, 6단계 마지막의 확인 절차로 직접 재 보는 것이 맞다. 내 구독을 연결해 쓰는 구성 자체는 국내 사용기와 영상 리뷰가 함께 다룬다 [8][20].

| 구간 | 값 | 무엇을 사나 |
|---|---|---|
| Free | 0달러, 월 500 크레딧 [4][5] | 내 구독을 연결하면 이것으로 충분한 경우가 많다 [8] |
| Pro | 월 20달러 [4] | 사용량 3배, 무제한 루틴, Ultrabrowse, Channels, 클라우드 핸드오프 [5] |
| Max | 월 200달러 [4] | 무엇을 더 사는지는 이번 조사에서 확인하지 못했다 |

**Pro는 모델 값이 아니라 기능 값으로 보는 것이 맞다** [8]. 루틴을 여러 개 굴리거나 원격 조종이 필요해질 때 넘어가면 된다. 연간 결제는 20퍼센트 싸다 [8].

**화면에서 확인할 것**: 설정의 모델 연결에 내 구독이 붙어 있고, 작업을 한 번 돌린 뒤에도 **크레딧 잔량이 그대로다.**

**막히면**: 크레딧이 계속 줄어들면 요청이 아직 Aside 자체 모델로 가고 있는 것이다. 모델 선택이 연결한 구독으로 되어 있는지 확인한다.

## 업무 효율은 어디서 나오나

**시간이 줄어드는 자리는 세 곳뿐이다.** 뭉뚱그리지 않고 갈라 보는 것이 중요하다.

| 줄어드는 자리 | 무엇이 사라지나 | 어느 단계가 가져오나 |
|---|---|---|
| 화면 이동 | 탭 열고 로그인 확인하고 찾아 들어가는 시간 | 2단계 |
| 설명 반복 | 매번 맥락을 다시 입력하는 시간 | 3단계 |
| 착수 지연 | "해야 하는데" 하고 미루는 시간 | 4단계 |

세 번째가 가장 크고 가장 안 세어진다. 매주 30분 걸리는 일을 미루다 금요일에 하는 사람에게 루틴이 주는 것은 **30분이 아니라 일주일의 부담**이다.

### 숫자로 만들어 보기

⚠️ **아래는 실측이 아니라 계산 예시다.** 자기 1단계 실측값을 넣어 다시 계산할 것.

**가정**: 주 2회, 회당 25분 걸리는 화면 취합 업무. Aside에 맡기면 지시와 검토에 회당 6분.

| 항목 | 지금 | Aside 도입 후 |
|---|---|---|
| 회당 시간 | 25분 | 6분 |
| 주간 시간 | 50분 | 12분 |
| 월간 시간 (4.3주) | 215분 | 51.6분 |
| 월 절감 | 기준 | 163.4분 (약 2시간 43분) |

**그런데 이 표는 첫 달에 맞지 않는다.** 이 가이드를 따라가는 데 90분이 들고, 2주간 하루 10분씩 손보는 데 140분이 더 든다. 합 230분이다.

| 회차 | 누적 투입 | 누적 절감 | 순이익 |
|---|---|---|---|
| 1개월 | 230분 | 163.4분 | 마이너스 66.6분 |
| 2개월 | 230분 | 326.8분 | 플러스 96.8분 |
| 3개월 | 230분 | 490.2분 | 플러스 260.2분 |

**본전은 2개월 차에 넘는다.** 첫 달에 손해라는 것을 알고 시작하는 것과 모르고 시작하는 것은 다르다. 한 달 써 보고 "별거 없네" 하고 접는 일이 여기서 생긴다.

그리고 **효율이 목적이 아닌 경우도 있다.** 리서치·준법 쪽에서 Aside가 주는 것은 시간이 아니라 **증빙이 남는다는 사실**이다 [1]. 사람이 하면 캡처를 빼먹는다.

## 흔히 막히는 지점

**1. 루틴을 너무 빨리 건다.**
두 번 성공하기 전에 예약하면 **검증 안 된 작업이 자동으로 반복된다.** 만드는 단계와 제출하는 단계를 갈라 두라는 권고가 나온 것도 같은 이유다 [11]. 4단계의 체크 세 줄을 건너뛰지 말 것.

**2. 로그인에 보안문자가 끼는 사이트를 후보로 고른다.**
카카오 로그인 화면에서 보안문자와 세션 끊김 때문에 자동화가 실패한 사례가 보고돼 있다 [11]. 이건 Aside를 잘 쓰면 풀리는 문제가 아니다. **후보에서 빼는 것이 정답이다.**

**3. 화면 아래쪽이 안 읽힌 것을 모른다.**
게으른 로딩(lazy load)을 쓰는 페이지는 보이는 영역만 검사하면 **아래쪽 내용이 빠진 채로 결과가 나온다** [11]. 목록 개수가 아는 값과 맞는지 한 번은 대조해야 한다. "끝까지 스크롤해서"를 지시에 넣는 것도 방법이다.

**4. 외부 사이트 장애를 에이전트 잘못으로 읽는다.**
상대 사이트가 죽어 있어도 화면에는 그냥 실패로 보인다 [11]. 실패했으면 **그 사이트를 직접 열어 보는 것**이 첫 진단이다.

**5. 남의 절감 숫자를 내 기대치로 삼는다.**
리뷰어들은 출시 며칠 된 제품이라는 점과, 벤더가 관리하는 저장소의 주장은 중립 기관이 재현하기 전까지 마케팅으로 보라고 적는다 [15]. **이 가이드의 계산도 예외가 아니다** — 163.4분은 내가 세운 가정의 산출물이지 관측값이 아니다. 1단계에서 실측 시간을 재라고 한 것이 이 자리를 위한 것이다. 재 두지 않으면 2주 뒤에 **줄었다는 느낌만 남고 숫자가 없다.**

**6. 확인 대기가 한 사람에게만 걸려 있다.**
민감한 작업 앞에서 확인을 기다리는 설계는 옳지만 [1], 팀에서 쓰기 시작하면 질문이 바뀐다 — **그 확인을 누가 보고, 그 사람이 없을 때는 누가 보나.** 혼자 쓸 때는 안 드러나고 두 번째 사람이 붙는 날 드러난다. 이 2주는 혼자 하는 범위로 잡고, 확인 절차를 정하기 전까지는 결제·발송·게시를 후보에서 뺀다.

## 2주 실천 과제

**하루 10분씩 14일.** 위 계산의 투입 140분이 이 표다. 체크 칸을 실제로 채워 나갈 것.

**1주차 — 되돌릴 수 있는 것만**

```
□ 1일차  모델 구독 연결, 크레딧 잔량 확인 (6단계)   ← 먼저 붙인다
□ 2일차  후보 3개 적기 + 각각 실측 시간 재기 (1단계)
□ 3일차  하나 골라 읽기 작업으로 시키기, 출력 형태 지정 (2단계)
□ 4일차  메모리 열어 읽고 틀린 항목 고치기 (3단계 ①②)
□ 5일차  같은 일 지시문 절반으로 다시 시키기 (3단계 ③)
□ 주말   결과물 형태 확정 + 지시문 한 줄로 저장, 1주차 실측 시간 적기
```

**왜 구독 연결이 1일차인가.** 6단계를 2주차로 미루면 1주차 내내 Aside 자체 모델로 무료 크레딧을 태운다. 2단계가 스스로 "금방 닳는다"고 경고한 것과 어긋난다. **본문의 단계 순서는 「되돌릴 수 있는 것부터」 축이고, 과제 순서는 「돈이 안 새는 것부터」 축이다** — 둘이 다른 것이 정상이다.

**2주차 — 자동과 확장**

```
□ 1일차  루틴 걸기, 체크 세 줄 먼저 통과시키기 (4단계)
□ 2일차  루틴 결과 도착 확인, 안 왔으면 원인 적기
□ 3일차  Channels 또는 CLI 로 한 번 불러 보기 (5단계)
□ 4일차  후보 2번의 후보 선정과 실측까지만 (1단계 재사용)
□ 5일차  1주차에 저장한 지시문을 후보 2번에 맞춰 고치기
□ 주말   본전 계산하기 — 투입 시간과 누적 절감 비교
```

**두 번째 업무를 2주 안에 완주시키지 않는다.** 여기서는 선정·실측·지시문 수정까지만 하고 실행은 3주차로 넘긴다. 하루 10분을 지키려면 이 정도가 한계이고, **투입 140분이라는 전제를 깨지 않기 위한 것**이기도 하다. 완주는 2주차 절차를 한 번 겪은 뒤가 훨씬 빠르다.

**2주 뒤 자기 점검 세 문항.**

1. 루틴이 도는 것을 **내가 안 열어도** 결과를 받는가
2. 지시문이 **저장돼 있어** 다음 사람이 그대로 쓸 수 있는가
3. 줄어든 시간이 **실측 숫자**로 적혀 있는가

셋 다 예가 아니면 아직 붙은 것이 아니다. 하나씩 되짚는 편이 새 업무를 늘리는 것보다 낫다.

## 다음으로 할 것

- **후보 2번을 붙인다.** 첫 업무에 90분이 들었다면 두 번째는 30분이면 된다. 절차가 같고 메모리가 이미 있다.
- **지시문을 팀에 넘긴다.** 저장해 둔 한 줄이 곧 인수인계 문서다. 사람이 아니라 지시문이 일을 안다.
- **쓰기로 넓히기 전에 규칙을 정한다.** 결제·발송·게시를 맡기려면 확인 단추를 누가 언제 보는지 먼저 정한다 [1].
- **판단이 필요한 자리는 따로 본다.** 문의 분류처럼 확률로 가르는 일은 브라우저가 아니라 판단 모델 쪽이다 — 배경은 딥리서치 보고서 **[[Jev와 Aside]]** 에 있다.
- **다른 자동화와 비교해 본다.** API가 있는 일은 [[n8n으로 첫 자동화 워크플로우 만들기]] 쪽이 더 싸고 안정적이다. Aside는 API가 없는 자리를 메운다.
